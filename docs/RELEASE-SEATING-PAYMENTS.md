# Seating, reservations and payment methods

Online POS now includes Meja & reservasi and cashier Laporan penjualan. Open bills show red with start time and elapsed minutes; reservations show orange. Waiter cannot select occupied/reserved tables. Server table locks also enforce the same rule at submission; stale client displays cannot bypass it. Table status uses a separate open-order query to avoid overlooking old open bills outside the latest 1000 history records. Cancellation or complete payment releases occupancy. Partial receipts are not posted: split must settle the whole bill atomically.

Cashier/owner reserves a free active table with guest and optional arrival time. Reservation stays blocked until cashier/owner uses Tamu datang / lepas. No automatic reservation expiry or scheduled multi-slot reservation calendar. Waiter can see reservations but cannot create/release them. Database membership checks keep data workspace-scoped.

Payment methods are cash, credit card, debit card, QR/QRIS, bank transfer and other. “Split pembayaran” records up to 10 parts of one invoice, with exact total equality required. This is a split tender, not separate guest invoices, item-level bill splitting or partial deferred payment. A cash part stores allocated amount, tendered and change; noncash references are optional. Do not enter card numbers. Noncash payments are manually confirmed records: no terminal authorization, generated QR, gateway webhook or bank confirmation integration was added.

Back Office Tax & service accepts percentage rates with two decimals and a tax-on-service switch. Calculation order: menu subtotal minus discount → service → tax on net menu (optionally including service). Rates are snapshotted when an order is submitted; changing settings applies only to new orders. Existing orders from previous versions keep zero rates. Amounts round to nearest rupiah. These are configurable operational charges, not automatic jurisdiction-specific tax advice.

Cashier reports are enabled by current server membership role, including existing and newly created cashier accounts. Waiter remains excluded. Net menu revenue/HPP/gross profit exclude tax and service; the new payment report shows total collections, tax/service and applied amounts by method. Split contributes each part to its own method and counts split invoices separately. Payment CSV exports invoice, time, method, applied amount and optional reference. History reporting still has the existing 1000-order cap and device-local rolling periods.

Migration 012 retires cash-only v2 payment permissions and adds server-checked quote/v3 settlement. A retry of already-paid settlement creates no additional receipts. Underpayment or invalid split rolls back all payment rows and financial snapshots. Old browser tabs need a reload. Physical Bluetooth integration and browser/device acceptance are still unverified.

Validation: 18 Node tests; transactional Supabase tests for reservation authorization, waiter blocks, occupancy/reseat, immutable rates, discounted tax/service, atomic split and cash change, QR recording, report rights and tenant isolation. Existing transaction/restaurant regression tests use v3 settlement. Test fixtures roll back.

## Catalogue and basket layout

The POS product catalogue now fills the available width, with three product columns on phones. A fixed bottom bar shows the estimated total including current tax/service and a basket item count. Press the total to submit the order; this does not settle payment. The basket button opens a drawer to review/edit quantities, item notes, order type and order-wide note. Draft note and type survive catalogue rerenders. Empty carts disable submit; in-flight submission blocks additional clicks; failed requests keep the basket. Existing server idempotency, table/guest requirements and payment workflow remain enforced. Browser/mobile layout acceptance is not verified in this environment.

## Staff trace, photos and touch UI

Migration 013 snapshots creator name/role on each order, cashier name on payment, and cancellation actor name. Names come from staff records (owner falls back to profile name/email prefix) and are display-only; membership continues to enforce authorization. Historical records are backfilled using available current identity data; historical names before this release cannot be reconstructed exactly. Migration 014 recovers older cancellation actor/time from existing audit evidence. The void/cancel report groups whole cancelled bills, includes reason/actor/time/value and CSV, and keeps these values outside paid sales. It is not item-level void/refund reporting.

Product forms accept PNG/JPEG/WebP up to 10 MB and generate a bounded JPEG thumbnail (max 320px, 60000 data-URL characters). The transaction saves product/photo together and rejects SVG. Thumbnails are stored in the dedicated POS database; cached by per-product timestamp and fetched in batches only when changed, rather than each 15-second poll. This avoids a new paid storage service; a storage/CDN migration remains appropriate for very large catalogues. User-generated SVG and remote photo URLs are not accepted.

Basket notes/buttons are below the unit price; the order-wide note field is removed. Kitchen/Bar print already places each note directly under its item name with no prices. Tapping a product animates its image/icon toward the basket; reduced-motion settings suppress travel animation. Split edits assign the remaining bill amount to the next part; later parts reset to zero until explicitly allocated. Server still verifies the exact total.

Touch targets, scrollable dialogs, phone basket drawer and payment form spacing were improved. Workspace logo replaces the SUMS POS sidebar brand when configured. Every receipt, including section slips, and website footer shows Powered by SUMS POS. Browser, device, gesture and physical printer output acceptance remain unverified. Validation: 21 Node tests plus transactional database photo/actor/cancel tests, syntax check and build.

## Product variants

Product edit → Kelola varian & harga configures up to 30 variants with distinct selling prices, stock and active flags. Each variant is a separate stock SKU linked to the same workspace/root product; HPP follows the root. The catalogue shows one root tile with the lowest active price, then prompts for a variant. Basket/order/section print include its name; multiple variants of a product can coexist in a bill. Root photo is used for the picker animation. Server prices and stock remain authoritative. Selecting the base directly is rejected while active variants exist. Root name/category/HPP changes propagate to future variant sales while historical order lines remain unchanged. Migrations 015/016 and rolled-back variant integration tests validate pricing, per-SKU stock, mixed variants, guards and tenant isolation.
